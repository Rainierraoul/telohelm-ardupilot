## 1. Questions

Paper 2 tests Telohelm's learning loop on a simulated air-to-air refuelling task. Paper 3 moves the same learning core, unchanged, onto a copter flown by ArduPilot, the open-source autopilot, in ArduPilot's software-in-the-loop simulator (SITL), which runs the real autopilot code with simulated physics. Only the task pack is new: the plug-in that gives Telohelm each task's goal, raw readings and velocity command.

- RQ1, learning. Starting from a library that holds only the designer's velocity guard, does the unchanged core adopt a working procedure for each of five copter tasks, how often across independent learning runs, and with how many model calls, tokens, dollars and minutes?
- RQ2, quality. On held-out scenarios from the same tasks, how often do the adopted libraries meet the goal, compared with no procedure, a designer's hand-written controller and ArduPilot's own flight modes?
- RQ3, transfer. With no further learning and no model calls, do the adopted procedures meet the goal on (a) multi-gate courses they never trained on, (b) a published drone-racing track, the Split-S, and (c) a second simulator, Gazebo?

The velocity guard is a designer-written check, adopted from the start and never changed by learning, that rejects any command whose velocity components are not all finite numbers within the task's speed limits.

Two descriptive measures go with the questions. One is how the calm-learned libraries fail under disturbances (satellite-navigation jamming and spoofing, radio loss, gusts, a weakened motor, a threat zone that appears mid-flight), flown with learning off. The other is the timing of System 1. System 1 is the fast control step, where the adopted procedure decides each second without calling the model, and the measure is how long each of those decisions takes, so the paper can say what rate the procedures run at. Neither is a learning claim. Learning to recover from disturbances is the next paper's question.

- The task packs: `paper3/ardupilot/pack.py` at the freeze commit. Each task's contract fingerprint is recorded. It is a hash of what the pack tells Telohelm: the goal fields, the readings and the command format. The reach3d fingerprint has been `fb18162f…` since the first 3D run. Everything the packs tell Telohelm beyond the bare goal is listed from `DESIGNER-KNOWLEDGE.md` in the paper's method section.
- The autopilot: ArduPilot Copter 4.7.2 at commit `fb773567`, built for SITL, with one local build-flag change needed on macOS (`ardupilot/README.md`). It runs ArduPilot's own default copter settings (section 4.4).
- The learning model: Claude Sonnet 5.5 through the GEM gateway (Deakin's service that relays requests to models hosted on Amazon Bedrock), as `bedrock/au.anthropic.claude-sonnet-5-5`, with effort `high` (the model's reasoning-effort setting) and up to 64,000 output tokens. The requested model string, the model each reply says served it (taken from the response) and the dates of all scored runs are recorded. Server-side fallback to another model is something a request has to ask for, with a beta header in Anthropic's API. The gateway path in `claude_provider.py` never sends that header, and each reply's serving label is recorded from the response. The label is the gateway's own name for the model that served the reply. If a recorded label ever differs from the requested model, that learning run is reported with the difference and is not rerun. Cost is reported at the provider's list price from the recorded token counts; what Deakin's gateway charged is reported beside it where the gateway records it.
- Learning settings: up to 3 attempts per learning run. An attempt is one candidate procedure written in one conversation of one to three model calls. A candidate must meet the goal on all 3 learning scenarios to be adopted. Flight examples are on, as in paper 2's scored learning: these are moments from the learner's own earlier flights, shown in its learning requests. When a reply breaks the core's format rules, the core sends the problems back and asks again within the same attempt. That is a format repair.
- The judge: every flight is scored on the simulator's true state, not the autopilot's estimate. The true state includes the true vertical speed, and the landing judge's touchdown-speed test uses it. Before each flight the runner waits until the simulator's true position, altitude and vertical speed have arrived, and a flight whose truth never arrives does not start. If any of them is missing at a step, the flight stops and is a fault: its records are kept, and whether it is flown again is decided under section 7 before its outcome is read. The judge never falls back to the autopilot's estimate. Each step records how old the truth reading was.
- Simulation speed. Running the simulator faster than real time adds decision delay in simulated time, and on 1 November that changed Split-S times by tens of seconds (`SYSTEM1-SPEED.md`). Each phase's speed-up is fixed before freezing by one rule: the highest speed-up at which the pilot's median decision lag stays under 5% of the decision period. The decision period is 1 s in every runner, so the threshold is 0.05 s. The rule applies to the task-flight lag measure (section 4.5), which it was set from. The Split-S, the Gazebo flights and the decision-timing measure run in real time. Measured on 2 November 2026 with the reference controller on five development reach scenarios (`runs/pilot-lag-reach-x*`), median lag was 0.0 s in real time, 0.1 s at twice real time, 0.2 s at five times and 0.5 s at ten times, and at ten times the same five flights took 128 steps against 88. Only real time meets the rule, so every scored phase runs in real time. The pilot's task flights confirmed this (section 8: median lag 0.001 s over 4,228 held-out steps), and the speed-up question is closed. Lag comes in steps of 0.1 s, so a median near zero can hide late decisions. The paper therefore reports, beside each median, the share of decisions at least 0.1 s late. In the pilot's held-out flights that was 1,017 of 4,228, and 21 of those were 0.2 s late.
- Up to four simulators at once. SITL flight phases and learning runs run up to four at once, each on its own simulator instance (10 to 13). A simulator instance is one copy of the simulator with its own network ports. Gazebo flights run alone. Model calls happen between flights and never inside a flight's control loop: the model writes a procedure, then the procedure flies without it. On 2 November, 2, 4 and 7 copies of the speed-up check (the reference controller on five development reach scenarios) flew together. Every flight took the same number of steps as the same flight alone (88 over the five), the median lag stayed 0.0 s and the largest was 0.101 s (`protocol/parallel_lag.py`, `runs/pilot-par*`). An eighth copy, on instance 14, could not start because its port, 5900, is the Mac's screen sharing; it says nothing about load. On 3 November 2026, from 09:22 to 09:38 AEDT, four new pilot learning runs (reach, reach3d, orbit and land) ran at once on instances 10 to 13, on the same development seeds as the pilot's learning runs (9001 to 9003). All four adopted a procedure on the first attempt, with 2, 2, 2 and 3 model calls (land's third call was a second format repair). Nine model calls completed, no per-call usage record (the token counts the gateway returns) shows a provider error, every reply was served by the requested model, and the runs took 11.5 to 16.1 minutes against 11.7 to 15.8 for the pilot's runs flown one at a time on 2 November. The largest decision lag in their learning flights was 0.101 s, the same as in those pilot runs (records in `runs/pilot-learn4-*`). A transport retry is the SDK resending the same request after a network or server error. The Anthropic SDK retries twice by default and those retries are not logged, so the records cannot show that no transport retry happened. Every learning flight's lag is recorded and reported. Before each phase the runner checks that its own instance's ports are free, that no Gazebo server runs, and that at most three other simulators run, all on scored instances. Each phase's manifest records its instance and what else was flying. The check exists because two development runs overlapped on 1 November. The lag of every scored flight is reported, so any effect of sharing the machine would show.

## 3. Tasks

Five copter tasks, each with its goal checked on true state:

| Task | Goal, with target ranges from the scenario generator |
|---|---|
| reach | Fly to a point 30 to 50 m away at fixed height and hold within 2 m for 5 s |
| avoid | Fly to a point 45 to 55 m away and hold, keeping out of a no-go zone of 8 to 12 m radius placed across the straight path |
| orbit | Fly clockwise laps round a point 25 to 35 m away at a radius of 15 to 22 m |
| land | Come down on a point 20 to 35 m away, slowly enough at touchdown |
| reach3d | Fly to a point 30 to 50 m away and 8 to 30 m up, and hold within 2.5 m for 3 s |

For the threat disturbance family only, the targets of reach, reach3d and land lie 39 to 51 m away (section 8.3, change 1).

The exact goal parameters come from `pack.py` at the freeze. The racing task (`race3d`) is left out: learning it needed a staged time limit and a seeded start, and it has not adopted at the task's own limit.

## 4. Design

### 4.1 Learning (RQ1)

For each task, 5 independent learning runs, each with its own three learning scenarios drawn from reserved seeds, starting from a library that holds only the designer's velocity guard. R = 5 was fixed before the pilot, on the strength of the one or two development runs per task that already adopted, so the pilot was only a check of the pipeline. Adoption is reported as a count out of five. Five of five gives a Wilson 95% interval of 0.57 to 1.0 and four of five gives 0.38 to 0.96, so RQ1 answers "how often" coarsely, which is enough for a platform study.

Per run, record: adopted or not; attempts and model calls to adoption; input and output tokens; cost at the provider's list price; wall-clock time; and the adopted source and its hash.

### 4.2 Quality on held-out scenarios (RQ2)

Each adopted library flies a held-out test set for its task: 20 calm scenarios and 10 in steady wind, from reserved seeds that no learning run uses. Every condition flies the same scenarios, so comparisons are paired.

Comparators, flown on the same test sets:

- No procedure: the drone holds still. This shows the task is not met by doing nothing.
- The designer's reference controller for each task (`demo.REFERENCE` in the code), hand-written and never shown to the learner.
- ArduPilot's own modes where one does the task, held to the procedures' limits (5 m/s horizontal, 2 m/s up and down): guided position targets for reach and reach3d, circle mode for orbit, and a guided flight to the point followed by land mode for land. ArduPilot has no mode that flies round an arbitrary no-go zone, so avoid has no autopilot comparator. The ArduPilot-mode comparators met the goal on all 20 of their pilot flights.

### 4.3 Transfer (RQ3)

Each adopted reach library and reach3d library, with learning off and no model available:

- (a) Courses. The reach procedure flies 30 flat multi-gate courses and the reach3d procedure 20 courses that climb one face of a building, cross the roof and drop the far side, from reserved course seeds. About half the courses carry a steady wind, as the generators draw it. A mission plan hands the procedure one gate at a time, and that sequencing is scripted, which the paper states. A gate counts when the straight path the drone flew between two decisions, on its true position, passes within 1 m of the gate's centre, gates in order (horizontal distance on flat courses). The Split-S uses the same rule. The generators build courses that are flyable by construction; the geometry check in the code adds nothing to that (`REVIEW-CODE-20261102.md`). Every course is flown by every condition. The designer's reference controller flies every course in SITL with the same wind, and its results are reported as a comparator. A course built to be flyable can still defeat the reference, because the wind, the 5 m/s speed limit and the 1 m gate rule act together. The headline counts every course, for every condition. Beside it, the analysis reports the learned procedures' counts on the courses the reference completed, and lists the courses the reference failed. Leaving out courses a comparator fails would select on that comparator's failure, so the subset is shown only for comparison.
- (b) The Split-S. The reach3d procedure flies the Split-S track, recreated from the University of Zurich Robotics and Perception Group's published gate coordinates with the published handedness (development flights before 2 November flew a mirror image; `REVIEW-CODE-20261102.md`), in real time at one decision a second, 5 flights per library, the reference controller flying it too. A gate counts when the straight path between two decisions passes within 1 m of it, in order. The drone starts from a 5 m hover at the published start position instead of the published 1.2 m start, so times cannot be compared with published racing times.
- (c) Gazebo. The reach3d procedure of each adopted library flies the Split-S 3 times in Gazebo, and the reference controller 3 times. Each flight uses a fresh Gazebo server, runs alone on the machine and in real time, and uses the same course, gate rule and decision period as in SITL. ArduPilot takes its physics from Gazebo through ArduPilot's Gazebo plugin (github.com/ArduPilot/ardupilot_gazebo, commit `f116b035`, built without its camera-streaming parts). The world (`ardupilot/gazebo/worlds/splits_open.sdf`) is an open field with no obstacles and no gate models, so the change from SITL is the physics. It keeps the development flights' 1 ms physics step and their copter model, iris_cine, which carries two cameras nothing reads (the stock iris model once reported an inverted attitude on the ground and would not arm). The development Gazebo flights flew a warehouse at true scale; those scripts and their attribution are in `ardupilot/gazebo/`. The scheduler test of 2 November flew one learned and one reference Gazebo flight through the scored runner, and both passed all 19 gates (section 8.2).

### 4.4 Disturbances (descriptive)

Each adopted library flies 5 scenarios from each disturbance family per task, learning off, using the disturbance generator (`battle.py` in the code), from reserved seeds. Orbit has no threat family. Results are reported per family, with how each flight ended. All six families are reported in one table, and the table marks the two where the autopilot ends the flight.

| Family | Who is in control |
|---|---|
| Spoofing | The procedure |
| Gusts | The procedure |
| Weakened motor | The procedure |
| Threat zone | The procedure |
| Radio loss | ArduPilot's failsafe: return-to-launch |
| Jamming | ArduPilot's failsafe: landing |

The simulator runs ArduPilot's own default copter settings. `Tools/autotest/default_params/copter.parm` sets `FS_THR_ENABLE` to 1, so a lost radio link starts return-to-launch, and the firmware default `FS_EKF_ACTION` of 1 starts a landing when the position estimate fails, which is what jamming causes. The decision to keep these defaults was taken before any scored run. They are what a fielded copter flies with, and the study is about procedures under a real autopilot. Turning safety features off to give the procedure more to do is a question for the next paper.

Radio loss and jamming were reclassified after the pilot, which showed the autopilot taking the vehicle from the procedure in every flight of both families (section 8.3, change 2). They are reported as tests of ArduPilot's own failsafes, its built-in responses to a lost link or lost satellite navigation, and the paper says so.

Threat zones on reach, reach3d and land sit with their near edge 24 to 30 m from home and switch on by the drone's distance from that edge, so that at the speed limit the procedure first sees each zone at least 9 m away (section 8.3, change 1).

### 4.5 Decision timing (descriptive)

From every flight: the decision lag and the procedure's run time per step, reported as medians and 95th percentiles, with the share of decisions at least 0.1 s late. The lag is measured in two ways, reported separately.

- Task flights (learning, held-out, comparators, disturbances): simulated time from the scheduled observation to the command. The 5% rule of section 2 applies to this measure.
- Course, Split-S and Gazebo flights: the newest telemetry time after the command minus the time of the position the decision used. This includes that position's age, so it is at least one telemetry period (0.1 s) by construction and cannot be held to the 5% rule. It is reported to compare conditions with each other.

The procedure's run time is recorded at every step of every flight, kept apart from the decision lag: wall-clock and processor seconds for the procedure, and separately for the guard. Task flights keep them in the core's decision log. Course, Split-S and Gazebo flights, flat courses included, keep them in their hash-chained log (section 6).

## 6. Analysis

Descriptive, with uncertainty. Every scored record's hash-chained log is verified before analysis. A hash-chained log is a record file in which each line carries the hash of the line before, so an edit or deletion shows. Each has a heads file, a separate file that keeps the chain's hash after every line. Proportions (adoption across runs, goals met, courses completed, gates passed) get Wilson 95% intervals. Paired comparisons on the same scenarios get the difference in proportions with a 95% percentile bootstrap interval: over scenarios for one library, and over learning runs and then scenarios within them when libraries are pooled (the two-level bootstrap), because flights by the same library are not independent. Costs get medians and ranges across runs. The unit of analysis for RQ1 is the learning run; for RQ2 and RQ3 results are reported per library and pooled across libraries. The analysis script is written and frozen with this protocol and runs once on the scored records.

Attribution, for every adopted procedure, with the attribution check (`attribution.py`): a memorisation scan for numbers from its run's learning scenarios in its code; a check that no line of any task's reference controller reached the model's requests; and a check that no reserved test seed or test scenario value did. Results are reported per library. The check for held-out numbers in the learning requests has a chance baseline: never-flown control scenarios (calm seeds 22001 to 22020, wind 23001 to 23010, reserved in `seeds.json`) are searched for in the learning requests the same way as the held-out ones, so a hit rate can be read beside the control search's rate. The control scenarios give a baseline for chance matches of held-out numbers in learning requests only. The search looks for lines from the reference controllers and from the hold-still comparator's code longer than 25 characters and for exact number patterns, so it does not catch equivalent code or other ways of writing a number, and a positive-number pattern can match the size of a negative number. Hits and denominators are reported beside the control search. A small count is not a finding of chance level, and the check cannot show the absence of memorisation. Any later change to the matcher applies equally to held-out and control records and is a deviation. Each attempt is one conversation, and every request resends the earlier turns, so from the second request on the model's own reply is part of the request. A reference-controller line therefore counts as reaching the model only if it is in a request before the model wrote it. Every flight's record names the procedure that made each decision, and the paper reports the share of control steps that no adopted procedure decided.

Before any result is computed, a validation step checks that every scheduled phase is present and finished: the 25 learning runs, then the flight phases implied by which runs adopted. A learning run that finished without adopting counts as a non-adoption; a learning run that is missing or crashed is a fault. Each phase must hold exactly its scheduled scenarios, repeat rounds and flights, each once. Every hash-chained log must have its heads file and check against it, including the logs of candidate trials. Result files must agree with each flight's own record and hash-chained log. All phases must share one protocol hash, one seeds hash, one learning-core wheel and one fingerprint of the executed paper 3 source (the runner, task-pack and scheduler files, and the Gazebo world and models). Each phase's manifest also records the repository commit, which can move during a run because other work is committed to the same repository. If any check fails, the analysis writes a report marked as a diagnostic, not a result, and exits with an error, and the scheduler reports it. Nothing is rerun automatically.

The lag and run-time summaries count each flight once; candidate trial flights during learning are included, and the copies of earlier flights that the core shows the model as examples are not counted again. The lag summaries cover all phases, including the ArduPilot-mode comparators and the disturbances, and the run-time summaries cover every phase in which a procedure flies. For RQ3, courses, Split-S and Gazebo are reported per library and pooled across libraries, and learned against reference on the same courses with the two-level bootstrap used for RQ2. The pooled Wilson intervals treat flights as independent although flights share scenarios and libraries, so they describe the flights flown, and the two-level bootstrap is the comparison measure. Five learning runs per task do not support claims about learning runs in general.

Repeatability: per task, the reference controller and the task's first adopted library (lowest run number) fly calm seeds 20001 to 20005 three times each, and the paper reports how often the three endings agree. Seeds 20001 to 20005 are also the first five held-out calm scenarios, so each is flown four times in all, and agreement is counted over the three repeat rounds only. Hold still is not repeated, because it always times out, and neither are the autopilot modes, which are not the object of study. The simulator does not repeat a flight exactly.

Expectations stated before the runs, to help interpret the results; none is a pass mark: adoption in most runs for each task, at a few cents of model cost per adoption; held-out goal rates for learned libraries near the reference controller's; and course and Split-S transfer for reach3d close to what development runs showed.

## 7. Faults and reruns

A flight may be rerun only for an infrastructure fault detected before its outcome is read: the simulator failed to start, the MAVLink connection dropped before the first command, or the runner crashed. A flight stopped because the simulator's truth was missing (section 2) is also an infrastructure fault under this rule. Every rerun is logged with its reason. A gateway error during learning is retried under the core's own retry rule and counted; the SDK's transport retries beneath that are not logged (section 2). Every other flight counts as flown.

### 8.3 What it changed

Each change is a decision with its reason. Commit IDs are given so Codex can check the code. The paper describes the final design only; this protocol records the changes.

1. Threat zones on reach, reach3d and land are placed across the straight path with their near edge 24 to 30 m from home, and switch on at the first step that begins with the drone's true position within 19 m of the edge. The procedure first sees a zone in the reading after that step. So a zone switches on after the drone has flown at least 5 m, and at the 5 m/s speed limit with one decision a second the procedure first sees it at least 9 m from its edge: up to one step (5 m) passes before the trigger is checked and one more before the reading shows the zone. Nine metres at the speed limit is almost two seconds to turn away. The 9 m follows from the geometry and the 5 m/s cap on commanded speed. The drone can travel further than 5 m in a step, so the analysis reports the true distance at which each threat flight first saw its zone, and a flight that saw it closer than 9 m is reported like any other. Whether the drone is inside a zone, or has hit a building on a course, is checked once per step, at the decision. The target lies 3 m or more beyond the zone (at least 2.97 m once positions are rounded to 0.1 m), which is more than any task's goal radius (2 m for reach, 2.5 m for reach3d, 1.5 m for land). Missions too short for this geometry are moved out along the same bearing, so these three tasks' threat targets lie 39 to 51 m away. The move applied to 2,279 scenarios for reach, 2,289 for reach3d and all 3,006 for land, of the 3,006 seeds checked per task: 1 to 3,000, the five reserved disturbance seeds 30001 to 30005 and the pilot seed 9201. Stepping a drone at full speed straight at the target over the same seeds gave a switch-on after at least 5 m, a least distance at first sight of 9.0 m and a least target clearance of 2.97 m. No scenario of any other family changed, and the avoid task's threat placement is unchanged. The reason for the change is that the pilot's first threat generator (zones at second 1 to 3) put a zone 1.3 m ahead of a land flight, and the second (timed by progress, section 8.2) let the procedure first see one 4.2 m away, so both measured the generator and told us little about the procedure. Check flights with the pilot's learned libraries on development seeds 9201 to 9204 (`runs/pilot-threat-edge-*`) switched every zone on after the drone had flown 7.1 to 12.1 m, and the procedure first saw it 9.6 to 14.0 m from its edge. Reach and reach3d kept out of all 8 zones and met their goals. Land entered 1 zone (first seen 10.2 m away) and kept out of the other 3 but timed out without landing. (`4d999054`; the two earlier generators were `5a039f96` and `3c3fce08`)

2. Radio loss and jamming are reported as tests of ArduPilot's own failsafes, separately from the four families where the procedure stays in control (section 4.4 gives the settings and the reason for keeping the defaults). They were reclassified after the pilot, because the autopilot takes the vehicle away from the procedure. In development, 1,044 of 1,172 flights with radio loss and 1,034 of 1,246 with jamming ended in an autopilot return-to-launch or landing; in the pilot, all of them did. `protocol/failsafe_tally.py` prints the development counts.

3. Flat courses now record each decision's lag, and the analysis reads course and Split-S lags, so the timing measure covers every flight type. (`5a039f96`)

4. The attribution check gets a chance baseline, described in section 6. The control scenarios (calm seeds 22001 to 22020, wind 23001 to 23010) clash with none of the 2,178 development identities that `protocol/make_seeds.py` scanned. Without a baseline, a few matching numbers in a request could not be told from coincidence. In the pilot, avoid's requests held 2 of 128 held-out numbers and 2 of 123 control numbers, reach's 1 of 57 and 0 of 61, and the others none, which is in line with the control search's rate. The reference-controller rule also changed (section 6 gives the reason), and the check now covers the lines of every task's reference controller. In the pilot no reference line reached a request before the model wrote it. The model itself wrote 2 distinct lines that match reference lines, both generic return statements (`return {'vn': vn, 've': ve}` and `return {'vn': 0.0, 've': 0.0}`). (`10d61e05`)

5. The runner gained a Gazebo phase, which the pilot found missing (section 4.3). The scheduler test flew it through the runner. (`e95642d0`)

6. Flights may run four at once (section 2). The time estimate in section 10, item 7 assumes this. (`44233df3`)

7. Every course is flown by every condition, and the headline counts every course (section 4.3). Before, a course the reference controller failed was not to be flown by the learned procedures at all. Now the records are complete and the analysis reports the learned counts on all courses and on the courses the reference completed, so the selection can be seen. (`44233df3`)

8. Repeatability was narrowed after the pilot. Draft 2 had 5 held-out scenarios per task and condition flown three times each. Now only the reference controller and the task's first adopted library repeat, because hold still always times out and the autopilot modes are not the object of study. Calm seeds 20001 to 20005 are also the first five held-out scenarios, so each is flown four times, and agreement is counted over the three repeat rounds only (section 6).
