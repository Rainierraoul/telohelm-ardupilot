## 1. Questions

Paper 2 tests Telohelm's learning loop on a simulated air-to-air refuelling task. Paper 3 moves the same learning core, unchanged, onto a copter flown by ArduPilot, the open-source autopilot, in ArduPilot's software-in-the-loop simulator (SITL), which runs the real autopilot code with simulated physics. Only the task pack is new: the plug-in that gives Telohelm each task's goal, raw readings and velocity command.

The velocity guard is a designer-written check, adopted from the start and never changed by learning, that rejects any command whose velocity components are not all finite numbers within the task's speed limits.

Three terms are used throughout. A scenario is one flight set-up: its goal, target, wind, heading and any event. A learning run is one run of the core that starts with only the velocity guard in its library and tries to write and adopt a procedure for a task, using three learning scenarios. A library is what a learning run leaves behind when it adopts a procedure.

The study has two parts.

### Study 1: platform and transfer

- RQ1, learning. Starting from a library that holds only the designer's velocity guard, does the unchanged core adopt a working procedure for each of five copter tasks, how often across independent learning runs, and with how many model calls, tokens and dollars, and how many seconds of wall-clock time (the analysis gives seconds per run)?
- RQ2, quality. On held-out scenarios from the same tasks, how often do the adopted libraries meet the goal, compared with no procedure, a designer's hand-written controller and ArduPilot's own flight modes?
- RQ3, transfer. With no further learning and no model calls, do the adopted procedures meet the goal on (a) multi-gate courses they never trained on, (b) a published drone-racing track, the Split-S, and (c) a second simulator, Gazebo?

Reach, reach3d and land each have 8 learning runs for Study 1. These are the calm arm of Study 2, defined next. Avoid and orbit each have 5 learning runs on ordinary calm scenarios, as in the first protocol.

Two secondary measures are new. Both sit beside the primary measures, which stay goal met (RQ2) and course completed (RQ3).

- Capped seconds on held-out scenarios. This is the seconds a flight took to meet its goal, with a flight that failed counted at its time limit, so that an early failure does not look fast. The report gives learned minus the reference controller and learned minus ArduPilot's modes.
- Decision steps to finish a course, learned minus the reference controller, on the courses both completed. The number of library-course pairs that qualify is given beside the number scheduled, because limiting the comparison to courses both completed selects on success.

### Study 2: learning under threat (RQ4)

- RQ4. For reach, reach3d and land: does learning and qualifying on scenarios that contain a threat zone change how often the acquired procedures meet the goal when a threat zone appears mid-flight, against learning and qualifying on the same layouts with the zones removed?

A threat zone is a circular area the drone must keep out of, which switches on during the flight (section 4.4 of this protocol describes how). The treatment is learning and qualification with threats together. The core qualifies a candidate procedure by flying it on the three learning scenarios, so a threat-arm candidate has to cope with a zone to be adopted. The study measures the effect of that whole treatment. It cannot say whether failure feedback or the harder qualification test causes any difference, or whether extra model calls under the same cap matter. The calls, attempts and cost of both arms are reported.

Study 2 uses the following terms.

- A block is one matched pair of learning runs for one task: the same three layouts, learned once with threat zones and once without. A task has 8 blocks, numbered 0 to 7.
- An arm is one side of the pair. The threat arm learns on the layouts with their zones. The calm arm learns on the same layouts with the zones removed.
- The matched family is the set of scenarios the calm arm learns on: for a seed, the threat family's scenario with its zone taken out (section 3).

Two descriptive measures go with the questions. One is how the Study 1 libraries fail under disturbances (satellite-navigation jamming and spoofing, radio loss, gusts, a weakened motor, a threat zone that appears mid-flight), flown with learning off. The other is the timing of System 1. System 1 is the fast control step, where the adopted procedure decides each second without calling the model, and the measure is how long each of those decisions takes, so the paper can say what rate the procedures run at. Neither is a learning claim. Learning to recover from the other disturbances is a later paper's question.

## 2. What is fixed

- The learning core: the same built Telohelm wheel (a built Python package file) that paper 2's scored streams and the first protocol's run used, SHA-256 (a fingerprint of a file's bytes) `bb2c6e779b7526c85fb6ced29bd0db01f0d30a88a16e2252f2f058cab3ce2f8c`, installed into its own environment for paper 3's scored runs. The runner checks the installed package against that wheel and refuses to start if they differ. The editable source tree `paper2/telohelm/src` may change after paper 2's scoring ends, so the wheel is the fixed reference.
- The task packs: `paper3/ardupilot/pack.py` at the freeze commit. Each task's contract fingerprint is recorded. It is a hash of what the pack tells Telohelm: the goal fields, the readings and the command format. Everything the packs tell Telohelm beyond the bare goal is listed from `DESIGNER-KNOWLEDGE.md` in the paper's method section.
- The autopilot: ArduPilot Copter 4.7.2 at commit `fb773567`, built for SITL, with one local build-flag change needed on macOS (`ardupilot/README.md`). It runs ArduPilot's own default copter settings (section 4.5).
- The learning model: Claude Sonnet 5.5 through the GEM gateway (Deakin's service that relays requests to models hosted on Amazon Bedrock), as `bedrock/au.anthropic.claude-sonnet-5-5`, with effort `high` (the model's reasoning-effort setting) and up to 64,000 output tokens. The requested model string, the model each reply says served it (taken from the response) and the dates of all scored runs are recorded. Server-side fallback to another model is something a request has to ask for, with a beta header in Anthropic's API. The gateway path in `claude_provider.py` never sends that header, and each reply's serving label is recorded from the response. The label is the gateway's own name for the model that served the reply, so it cannot reveal a substituted model. If a recorded label ever differs from the requested model, that learning run is reported with the difference and is not rerun. Cost is reported at the provider's list price from the recorded token counts, as a total only when every recorded call carries them (section 6). What Deakin's gateway charged is reported beside it where the gateway records it (section 6).
- Learning settings: up to 3 attempts per learning run. An attempt is one candidate procedure written in one conversation of one to three model calls. A candidate must meet the goal on all 3 learning scenarios to be adopted. Flight examples are on: these are moments from the learner's own earlier flights, shown in its learning requests. When a reply breaks the core's format rules, the core sends the problems back and asks again within the same attempt. That is a format repair. The settings are the same in both arms of Study 2.
- The judge: every flight is scored on the simulator's true state, not the autopilot's estimate. The true state includes the true vertical speed, and the landing judge's touchdown-speed test uses it. Before each flight the runner waits until the simulator's true position, altitude and vertical speed have arrived, and a flight whose truth never arrives does not start. If any of them is missing at a step, the flight stops and is a fault: its records are kept, and whether it is flown again is decided under section 7 before its outcome is read. The judge never falls back to the autopilot's estimate. Each step records how old the truth reading was.
- Simulation speed. Running the simulator faster than real time adds decision delay in simulated time, and that changed Split-S times by tens of seconds in development (`SYSTEM1-SPEED.md`). Each phase's speed-up is fixed by one rule: the highest speed-up at which the median decision lag stays under 5% of the decision period. The decision period is 1 s in every runner, so the threshold is 0.05 s. The rule applies to the task-flight lag measure (section 4.6). The Split-S, the Gazebo flights and the decision-timing measure run in real time. When the rule was measured on 2 November 2026, with the reference controller on five development reach scenarios, median lag was 0.0 s in real time, 0.1 s at twice real time, 0.2 s at five times and 0.5 s at ten times. Only real time meets the rule, so every scored phase runs in real time. Lag comes in steps of 0.1 s, so a median near zero can hide late decisions. The paper therefore reports, beside each median, the share of decisions at least 0.1 s late.
- Up to four simulators at once. SITL flight phases and learning runs run up to four at once, each on its own simulator instance (10 to 13). A simulator instance is one copy of the simulator with its own network ports. Gazebo flights run alone. Model calls happen between flights and never inside a flight's control loop: the model writes a procedure, then the procedure flies without it. Development checks in the first protocol's work found no change in flight length or lag when 2, 4 and 7 copies flew together, and four learning runs at once took as long as runs flown one at a time. A transport retry is the SDK resending the same request after a network or server error. The Anthropic SDK retries twice by default and those retries are not logged, so the records cannot show that no transport retry happened. Before each phase the runner checks that its own instance's ports are free, that no Gazebo server runs, and that at most three other simulators run, all on scored instances. Each phase's manifest records its instance and what else was flying. The lag of every scored flight is reported, so any effect of sharing the machine would show.
- Protocol version 2. The runner is started with `--protocol 2` (`ardupilot/scored.py`, `use_protocol`). It then reads `protocol/seeds-2.json` and requires `PROTOCOL-2.md` for scored phases. Every phase's manifest records the protocol version, the protocol file and its hash, and the seeds file and its hash.
- Source fingerprint: one hash over the executed paper 3 source, which is the Python files in `ardupilot/`, the Gazebo world and model files, `protocol/run_scored.py`, `protocol/seeds.json` and `protocol/seeds-2.json`. Every phase records it, and the validation gate (section 6) requires one value across all phases. The analysis and validation scripts are not in it. They run after the flights and record their own hashes in the analysis record.

## 3. Tasks

Five copter tasks, each with its goal checked on true state:

| Task | Goal, with target ranges from the scenario generator |
|---|---|
| reach | Fly to a point 30 to 50 m away at fixed height and hold within 2 m for 5 s |
| avoid | Fly to a point 45 to 55 m away and hold, keeping out of a no-go zone of 8 to 12 m radius placed across the straight path |
| orbit | Fly one clockwise lap round a point 25 to 35 m away at a radius of 15 to 22 m |
| land | Come down on a point 20 to 35 m away, slowly enough at touchdown |
| reach3d | Fly to a point 30 to 50 m away and 8 to 30 m up, and hold within 2.5 m for 3 s |

The exact goal parameters and time limits come from `pack.py` at the freeze. The ranges above are those of ordinary calm scenarios. The racing task (`race3d`) is left out: learning it needed a staged time limit and a seeded start, and it has not adopted at the task's own limit.

The threat family for reach, reach3d and land places the zone across the straight path, with its near edge 24 to 30 m from home and its radius 6 to 9 m. The zone switches on at the first step that begins with the drone within 19 m of its near edge, so the drone has flown at least 5 m by then. The procedure first sees the zone in the reading after that step. At the 5 m/s speed limit and one decision a second, that is at least 9 m from the edge: up to one step (5 m) passes before the trigger is checked and one more before the reading shows the zone. The drone can travel further than 5 m in a step, so the analysis reports the true distance at which each threat flight first saw its zone, for the disturbance flights and for Study 2's evaluation flights, where each library's name carries its block and arm (section 4.4). The trigger has a fallback: `pack.py` switches any progress- or distance-triggered event on at half the task's time limit if the trigger has not fired by then. The fallback cannot put a zone within 19 m of the drone, because the distance check would have fired first, so the 9 m claim stands. The target lies about 3 m or more beyond the zone, less the rounding of the target and of the zone centre to 0.1 m each. A target drawn too close to leave this room is moved out along its bearing, so targets in the threat family lie 39 to 51 m away (`ardupilot/battle.py`, threat branch). Orbit has no threat family. Avoid's threat zone sits beside its no-go zone and switches on at a second drawn from 1 to 3 of the flight, with no distance trigger (`ardupilot/battle.py`, threat branch).

The matched family (`battle.matched_calm`) takes the threat family's scenario for a seed and removes its zone: the goal, target, wind and heading are the same, and the scenario has no event. Its episode is named `matched-<seed>`, and the threat family's `threat-<seed>`. The name never reaches the model. The provider sends only the system prompt and the turns, and flight examples name episodes by an opaque alias (such as `episode-ad698db2`). A check of one pilot run found no raw name in it. Codex then checked all 30 saved model-start requests from the two stopped pilots, none of which holds a raw episode name, and a stub call through the provider, which receives only the model settings, the system prompt and the messages. The check covers the request as the client sends it, not anything the gateway does. The code asserts that these fields equal the threat scenario's. An ordinary calm scenario drawn with the same seed is a different place, because each scenario family draws from its own random stream. Land shows the difference most: ordinary calm land targets lie 20 to 35 m away, and threat-family land targets lie 39 to 51 m away. So Study 1's land libraries learn on targets 39 to 51 m away, because they are the calm arm of Study 2, and they are tested on held-out calm scenarios with targets 20 to 35 m away. Reach and reach3d differ too, because their ordinary calm targets lie 30 to 50 m away. Study 1's learning for these three tasks therefore uses the matched geometry and not the ordinary calm geometry of the first protocol, and the paper says so.

## 4. Design

### 4.1 Learning (RQ1 and Study 2)

- Reach, reach3d and land: 8 matched blocks each (b = 0 to 7). Block b has three layouts, whose seeds are `blocks[task][b]` in `seeds-2.json`: 40001 to 40003 for block 0, 40101 to 40103 for block 1, and so on up to 40701 to 40703 for block 7. In each block one learning run learns on the threat family (the threat arm) and one on the matched family (the calm arm), with the same core, model, budget and settings.
- Avoid and orbit: 5 learning runs each on ordinary calm scenarios, seeds `learning_calm[task][r]`: 40001 to 40003 for run 0, up to 40401 to 40403 for run 4. Each task has its own seed namespace, so these do not clash with the blocks.
- In all there are 58 learning runs: 24 in the threat arm, 24 in the calm arm and 10 on ordinary calm scenarios.
- Order (`protocol/run_scored.py`, `learning_jobs_2`): block by block. Within a block the two arms are queued together, in an order drawn for that task and block from `ORDER_SEED` 20261104. With four workers taking jobs from the queue, the two arms usually run at the same time, so the drawn order decides only which is taken first. The order in which the arms are evaluated uses a separate draw from the same seed. This spreads both arms through the same window of model use, which limits drift in the served model over time. It cannot verify the gateway's served model version.
- Adoption is reported out of every scheduled run in each arm. Five of five gives a Wilson 95% interval of 0.57 to 1.0, and eight of eight gives 0.68 to 1.0 (seven of eight gives 0.53 to 0.98). RQ1 and Study 2's adoption comparison therefore answer "how often" coarsely, which is enough for a platform study. A run that finished without adopting is a non-adoption. A run that is missing or crashed is a fault (section 7).
- Spending: the scheduler starts no further learning run once the finished runs reach US$12 at list price (`SPEND_LIMIT_USD_2`). It reads `claude_cost_usd` from the summary of each learning run that has a done mark, and counts a missing value as 0. A failed model call can carry no cost, and the summary adds it up as 0, so each figure is a known subtotal. Runs still under way are not read and are not interrupted, so the stop is a guard on known list-price spending and not an exact invoice ceiling. The stop can be moved with `run_scored.py run ... --spend-limit <US$>`. Raising it is Simon's decision. The scheduler logs the limit in its first line, and because it is an argument and not a source file, the source fingerprint does not change. The default is US$12. A limit of 0 is a real stop that holds every learning run, and does not fall back to the default. If a finished run's summary cannot be read, every later learning run is held, because the spending check raises on each call until the summary is repaired. A run that is not started is held for Simon's decision, and under the validation gate it is a missing run (section 6), so no result is computed until it runs or a deviation records its absence. The forecast is about US$5.70 (section 10).
- Learning is never paused (section 7).

Per run, record: block and arm where they apply; adopted or not; attempts and model calls to adoption; input and output tokens; cost at the provider's list price (each with the number of calls that carry it); wall-clock time; and the adopted source and its hash.

### 4.2 Quality on held-out scenarios (Study 1, RQ2)

Each adopted library flies a held-out test set for its task: 20 calm scenarios (seeds 41001 to 41020) and 10 in steady wind (41101 to 41110), from reserved seeds that no learning run uses. Every condition flies the same scenarios, so comparisons are paired. The libraries are the calm arm's, up to 8 for each of reach, reach3d and land (a non-adoption removes one), and up to 5 each for avoid and orbit.

Comparators, flown on the same test sets:

- No procedure: the drone holds still. This shows the task is not met by doing nothing.
- The designer's reference controller for each task (`demo.REFERENCE` in the code), hand-written and never shown to the learner.
- ArduPilot's own modes where one does the task, held to the procedures' limits (5 m/s horizontal, 2 m/s up and down): guided position targets for reach and reach3d, circle mode for orbit (which flies at 4 m/s, `ORBIT_SPEED_MS`, under the 5 m/s cap, so its capped seconds on orbit reflect that slower speed), and a guided flight to the point followed by land mode for land. ArduPilot has no mode that flies round an arbitrary no-go zone, so avoid has no autopilot comparator.

The secondary measure is capped seconds (section 1), learned minus the reference controller and learned minus ArduPilot's modes, per library with the scenario bootstrap and pooled over a task's libraries with the crossed bootstrap (section 6). Hold still never meets the goal, so it is not compared on time.

### 4.3 Transfer (Study 1, RQ3)

Each adopted reach library and reach3d library, with learning off and no model available:

- (a) Courses. The reach procedure flies 30 flat multi-gate courses (seeds 530000 to 530029) and the reach3d procedure 20 courses that climb one face of a building, cross the roof and drop the far side (seeds 630000 to 630019). About half the courses carry a steady wind, as the generators draw it. A mission plan hands the procedure one gate at a time, and that sequencing is scripted, which the paper states. A gate counts when the straight path the drone flew between two decisions, on its true position, passes within 1 m of the gate's centre, gates in order (horizontal distance on flat courses). A flat course stops after 900 decision steps and a building course after 1,200, at one decision a second. The generators build courses that are flyable by construction. Every course is flown by every condition. The designer's reference controller flies every course in SITL with the same wind, and its results are reported as a comparator. A course built to be flyable can still defeat the reference, because the wind, the 5 m/s speed limit and the 1 m gate rule act together. The headline counts every course, for every condition. Beside it, the analysis reports the learned procedures' counts on the courses the reference completed, and lists the courses the reference failed. Leaving out courses a comparator fails would select on that comparator's failure, so the subset is shown only for comparison.
- (b) The Split-S. The reach3d procedure flies the Split-S track, recreated from the University of Zurich Robotics and Perception Group's published gate coordinates with the published handedness, in real time at one decision a second, 5 flights per library, the reference controller flying it too. A gate counts under the same rule as on courses. The drone starts from a 5 m hover at the published start position instead of the published 1.2 m start, so times cannot be compared with published racing times.
- (c) Gazebo. The reach3d procedure of each adopted library flies the Split-S 3 times in Gazebo, and the reference controller 3 times. Each flight uses a fresh Gazebo server, runs alone on the machine and in real time, and uses the same course, gate rule and decision period as in SITL. ArduPilot takes its physics from Gazebo through ArduPilot's Gazebo plugin (github.com/ArduPilot/ardupilot_gazebo, commit `f116b035`, built without its camera-streaming parts). The world (`ardupilot/gazebo/worlds/splits_open.sdf`) is an open field with no obstacles and no gate models, so the change from SITL is the physics. It keeps the development flights' 1 ms physics step and their copter model, iris_cine, which carries two cameras nothing reads (the stock iris model once reported an inverted attitude on the ground and would not arm).

The libraries are the calm arm's, up to 8 for reach and for reach3d. The secondary measure is decision steps to finish a course (section 1), pooled over libraries with the crossed bootstrap (section 6), on the courses both the learned procedure and the reference completed, with the number of such pairs given beside the number of library-course pairs scheduled. The per-library differences against the reference, for completion, come with the scenario bootstrap.

### 4.4 Study 2 evaluation (RQ4)

- Every adopted library of both arms flies the same 20 fresh threat scenarios, seeds 44001 to 44020 in each task's own seed namespace, with learning off (`scored.py`, phase `threat`).
- The threat arm's libraries also fly the whole held-out set of section 4.2, 20 calm and 10 wind scenarios, 30 in all, so performance on ordinary scenarios can be compared between arms. The calm arm's libraries fly that set as part of Study 1. This comparison checks retention, and it is over all 30 scenarios. Without a stated margin it cannot show that threat training costs nothing in calm flight.
- Primary outcome, per task. For each block and each of the 20 scenarios, the outcome of an arm is 1 if that arm's learning run adopted and its procedure then met the goal, and 0 otherwise. A non-adopted arm has no evaluation flights and contributes 0 on every scenario, so the comparison does not drop the threat arm's failures to adopt. The effect is the mean of threat minus calm over all block-scenario pairs. The scenario identities and time limits are the planned ones, taken from the seeds file and the task and never from the flights that happened. A task on which no learning run adopts therefore keeps all 8 blocks: 20 threat scenarios, each counted at the task's time limit in both arms, and 30 held-out scenarios with no successes. An adopted library whose evaluation flights are missing or incomplete is a fault, never a 0.
- Both arms get the same goal text. It already says that `ctx.threats` lists the active zones and that entering one fails the episode (`SHARED_GOAL` in `pack.py`). The Study 2 treatment is therefore experience of zones in learning and qualification, not knowledge that zones exist.
- Secondary, per task and per arm: adoption; goals met given adoption; flights that entered a zone; capped seconds, threat minus calm (a non-adopted arm counts at the time limit); held-out goals over the 30 scenarios, threat minus calm; and model calls, attempts and list cost.
- The first-sight distance of section 3 is reported for every evaluation flight, library by library. For each arm the Study 2 entry also gives the number of evaluation flights whose zone switched on, how many of them first saw it under 9 m, and the least distance.
- Avoid is not in Study 2. In the first scored run, avoid-1, whose procedure never reads the threat input, met the goal in the same 2 of 5 threat flights as every other avoid library. That test could not tell a response to the zone from the zone's placement (section 8.1).
- Per-task effects are primary. No pooled effect across tasks is computed.
- Precedence: the primary outcome leads the paper's answer to RQ4. The retention check and the other secondary measures are reported beside it and do not override it. If they point the other way, the paper reports both and says so.

### 4.5 Disturbances (descriptive)

Each adopted Study 1 library flies 5 scenarios (seeds 43001 to 43005) from each disturbance family per task, learning off, using the disturbance generator (`battle.py` in the code). Orbit has no threat family. Results are reported per family, with how each flight ended. All six families are reported in one table, and the table marks the two where the autopilot ends the flight.

| Family | Who is in control |
|---|---|
| Spoofing | The procedure |
| Gusts | The procedure |
| Weakened motor | The procedure |
| Threat zone | The procedure |
| Radio loss | ArduPilot's failsafe: return-to-launch |
| Jamming | ArduPilot's failsafe: landing |

The simulator runs ArduPilot's own default copter settings. `Tools/autotest/default_params/copter.parm` sets `FS_THR_ENABLE` to 1, so a lost radio link starts return-to-launch, and the firmware default `FS_EKF_ACTION` of 1 starts a landing when the position estimate fails, which is what jamming causes. The decision to keep these defaults was taken before any scored run. They are what a fielded copter flies with, and the study is about procedures under a real autopilot. Turning safety features off to give the procedure more to do is a question for a later paper.

Reporting rules for this section:

- A configured disturbance is not always an exposure. A flight whose event never started stays in its family's denominator and is listed as unexposed.
- The realised effect is the largest error of the autopilot's position estimate from the true position after the event starts. Only samples strictly after the start step count, because the event starts during the step that ends at the start time, so the sample at the start time is from before it.
- Spoofing successes are split into goals met while the injection was still active and goals met after it ended.
- Jamming and radio loss are tests of ArduPilot's configured failsafes, its built-in responses to a lost satellite-navigation fix or a lost link. They are reported with each flight's actual ending, and the paper says so.

### 4.6 Decision timing (descriptive)

From every flight: the decision lag and the procedure's run time per step, reported as medians and 95th percentiles. The lag is measured in two ways, reported separately.

- Task flights (learning, held-out, comparators, disturbances, threat evaluation): simulated time from the scheduled observation to the command. The 5% rule of section 2 applies to this measure.
- Course, Split-S and Gazebo flights: the newest telemetry time after the command minus the time of the position the decision used. This includes that position's age, so it is at least one telemetry period (0.1 s) by construction and cannot be held to the 5% rule. It is reported to compare conditions with each other.

The share of decisions at least 0.1 s late goes with the lag summaries only. The procedure's run time is recorded at every step of every flight, kept apart from the decision lag. It is recorded as wall-clock and as processor seconds for the procedure, and separately for the guard, and the summaries give processor seconds beside wall-clock seconds. Task flights keep them in the core's decision log. Course, Split-S and Gazebo flights keep them in their hash-chained log (section 6).

## 6. Analysis

Descriptive, with uncertainty. The analysis script (`protocol/analysis.py`, run with `--protocol 2`) is written and frozen with this protocol and runs once on the scored records. It refuses to write into a folder that already holds an analysis, so a later reading goes to a new, separately named folder.

Every scored record's hash-chained log is verified before analysis. A hash-chained log is a record file in which each line carries the hash of the line before, so an edit or deletion shows. Each has a heads file, a separate file that keeps the chain's hash after every line. Proportions (adoption across runs, goals met, courses completed, gates passed) get Wilson 95% intervals. Paired comparisons on the same scenarios get the difference in proportions with a 95% percentile bootstrap interval: over scenarios for one library, and by the crossed bootstrap described below when libraries are pooled, because flights by the same library are not independent. Costs get medians and ranges across the runs whose every recorded call carries a cost, with the number of other runs beside them. The unit of analysis for RQ1 is the learning run; for RQ2 and RQ3 results are reported per library and pooled across libraries.

Study 2's comparison (`matched_block_difference`) is threat minus calm over every block-scenario pair of a task. Its 95% percentile interval comes from 10,000 resamples with seed 20261102. Each resample draws blocks with replacement and, separately, scenario identities with replacement. The same scenario draw applies to every drawn block, because all libraries fly the same cases, and both arms stay paired. Spread in either arm therefore widens the interval, and neither arm is treated as a fixed reference. The same procedure gives the intervals for the capped-seconds and held-out differences of section 4.4, the held-out difference being over all 30 held-out scenarios. The analysis takes the scenario identities and time limits from the seeds file and the task (`study2` in `analysis.py`), so a task on which no learning run adopts keeps all 8 blocks, as section 4.4 says.

Study 1's pooled comparisons use the same crossed draw (`crossed_difference` in `analysis.py`). These are the pooled held-out comparisons, the pooled capped-seconds comparisons, the pooled course completion difference and the course-step difference. Each of 10,000 resamples (seed 20261102) draws libraries with replacement and, separately, scenario identities with replacement, and applies the same scenario draw to every drawn library. Every library flies the same scenarios, so resampling scenarios separately inside each library would treat one scenario flown by eight libraries as eight independent draws and make the interval too narrow. The course steps are compared only on courses that both the library and the reference completed. For them the draws are over every scheduled course and every learned library, and each resample keeps the selected pairs it contains. A resample that contains none is set aside and counted (`empty_resamples`). The step result reports its pair count beside the scheduled count. Per-library comparisons keep the scenario bootstrap.

Also reported:

- the per-library course differences against the reference, with the scenario bootstrap;
- processor-second summaries (section 4.6);
- billed cost: a total only when every recorded call of a learning run carries a gateway charge, and otherwise null, with any charges that did arrive given as a known subtotal and the count of calls with a charge. List-price cost from token counts stays the cost measure. A failed model call can carry no cost or token counts, and the run summary adds those up as 0, so its figure is a known subtotal. The analysis gives list-price cost as a total only when every recorded call carries one, and otherwise as the known subtotal with the number of calls without a value (`list_usage`, `usage_totals`). Input and output tokens are treated field by field: each is a total when every call carries that field, and otherwise a known subtotal. `calls_with_token_counts` counts the calls that carry both. Every recorded call stays in the call count;
- the exposure rules of section 4.5;
- the threat arm's held-out flights are kept out of Study 1's pooled results.

Attribution, for every adopted procedure, with the attribution check (`attribution.py`): a memorisation scan for numbers from its run's learning scenarios in its code; a check that no line of any task's reference controller reached the model's requests; and a search of the learning requests for the test scenarios' numbers. That search covers only numbers with a decimal part (target coordinates, wind speed, zone centre and radius), searched with exact number patterns (the values are not rounded to integers), because whole numbers such as 21 occur in any request. Seeds are not searched. For reach, reach3d and land libraries the test scenarios include the threat evaluation cases, and their chance baseline includes never-flown threat controls (seeds 45001 to 45020). Results are reported per library. The search for test-scenario numbers has a chance baseline: the decimal numbers of never-flown control scenarios (calm seeds 42001 to 42020, wind 42101 to 42110) are searched for in the learning requests the same way as the test ones, so a hit rate can be read beside the control search's rate. The control scenarios give a baseline for chance matches of those decimal numbers only. The search looks for lines from the reference controllers and from the hold-still comparator's code longer than 25 characters and for exact patterns of decimal numbers, so it does not catch equivalent code or other ways of writing a number, and a positive-number pattern can match the size of a negative number. Hits and denominators are reported beside the control search. A small count is not a finding of chance level, and the check cannot show the absence of memorisation. Any later change to the matcher applies equally to held-out and control records and is a deviation. Each attempt is one conversation, and every request resends the earlier turns, so from the second request on the model's own reply is part of the request. A reference-controller line therefore counts as reaching the model only if it is in a request before the model wrote it. Every flight's record names the procedure that made each decision, and the paper reports the share of control steps that no adopted procedure decided.

Before any result is computed, a validation step (`protocol/validate.py --protocol 2`) checks that every scheduled phase is present and finished. The scored analysis runs with 8 blocks, and any other count is a deviation: the gate refuses a scored second-protocol check at any other count (`validate.py`). The scheduled phases are the 58 learning runs, each with the block and arm its name says and the learning family its manifest records, and then the flight phases implied by which runs adopted, including Study 2's threat evaluation phases. A learning run that finished without adopting counts as a non-adoption; a learning run that is missing or crashed is a fault. Each phase must hold exactly its scheduled scenarios, repeat rounds and flights, each once. Every hash-chained log must have its heads file and check against it, including the logs of candidate trials. Result files must agree with each flight's own record and hash-chained log. All phases must share one protocol hash, one seeds hash, one learning-core wheel and one source fingerprint, and each manifest must name `PROTOCOL-2.md`, `seeds-2.json` and protocol version 2. Each phase's manifest also records the repository commit, which can move during a run because other work is committed to the same repository. If any check fails, the analysis computes no outcome. It writes a report marked as a diagnostic, not a result, in which `analysis.json` and `report.md` hold the gate's errors only (`outcomes_withheld`). Adoption is not hidden by this, because the flight schedule depends on it: the scheduler's log line after learning (`adopted:`) gives the number of Study 1 libraries and the number of Study 2 arms that adopted, counting both arms. The gate's count in the diagnostic (`adopted_libraries`) is the number of Study 1 libraries only: the calm arm's for reach, reach3d and land, and the libraries of avoid and orbit. It leaves out the threat arm's, so it does not show how many threat-arm runs adopted. The operating rule on reading outcomes covers flight outcomes. The analysis exits with an error, and the scheduler reports it (`main()` in `analysis.py`). If the gate passed and the analysis raises, the error stands and no report is written. Nothing is rerun automatically.

Operating rule: nobody reads flight outcomes before the gate passes. Each phase's log prints every flight's outcome as it lands, so for the logs this is a rule and not something the code enforces. The analysis itself withholds every outcome when the gate fails. The rule binds the agents that run and review the study, and Simon.

The lag and run-time summaries count each flight once; candidate trial flights during learning are included, and the copies of earlier flights that the core shows the model as examples are not counted again. The lag summaries cover all phases, including the ArduPilot-mode comparators and the disturbances, and the run-time summaries cover every phase in which a procedure flies. For RQ3, courses, Split-S and Gazebo are reported per library and pooled across libraries, and learned against reference on the same courses with the crossed bootstrap used for RQ2. The pooled Wilson intervals treat flights as independent although flights share scenarios and libraries, so they describe the flights flown, and the crossed bootstrap is the comparison measure. Five learning runs per task for avoid and orbit, and eight for the other three, do not support claims about learning runs in general. Eight blocks per task give a coarse library-level interval for RQ4, and the paper reports each task's effect and interval whatever their sign. The scale of one non-adoption is large: with 8 blocks and 20 scenarios, one non-adoption in one arm moves a task's difference by 0.125 on its own (one block of eight, at a goal rate of 1). A percentile bootstrap over 8 blocks is approximate, and its interval leans on the spread between those 8 blocks.

Repeatability: per task, the reference controller and the task's first adopted calm-arm library (lowest block) fly calm seeds 41001 to 41005 three times each, and the paper reports how often the three endings agree. Seeds 41001 to 41005 are also the first five held-out calm scenarios, so each is flown four times in all, and agreement is counted over the three repeat rounds only. Hold still is not repeated, because it always times out, and neither are the autopilot modes, which are not the object of study. The simulator does not repeat a flight exactly.

No expectation is stated for the direction or size of RQ4's effect. For Study 1, the expectation is adoption in most runs for each task at a few cents of model cost per adoption, and held-out goal rates for learned libraries near the reference controller's. It is not a pass mark.

## 7. Faults and reruns

A flight may be rerun only for an infrastructure fault detected before its outcome is read: the simulator failed to start, the MAVLink connection dropped before the first command, or the runner crashed. A flight stopped because the simulator's truth was missing (section 2) is also an infrastructure fault under this rule. Every rerun is logged with its reason. A gateway error during learning is retried under the core's own retry rule and counted; the SDK's transport retries beneath that are not logged (section 2). Every other flight counts as flown.

The gate has no exception path. If a phase cannot be completed after reruns under this rule, the study has no gated result. Simon decides what follows, and any reading of the records is then a deviation analysis, labelled as such, and names the missing phase.

A learning run that crashes is a fault. The crashed folder is moved out of the run root and kept, because the gate would flag it as unscheduled there. The rerun uses the scheduled name and the same seeds and makes new model calls, and both the crashed run and the rerun are listed in the deviations file.

A crashed flight phase is rerun the same way. Its half-done folder is moved out of the run root and kept, together with its phase log (`logs/<phase>.log`), because the rerun writes a new log under the same name. The rerun uses the scheduled name, and both go in the deviations file.

The analysis folder. The scheduler writes the analysis into the first unused folder, `analysis`, then `analysis-2` and so on (`analysis_folder` in `protocol/run_scored.py`), and logs which. After a failed gate and a rerun, the same command therefore writes the new analysis beside the diagnostic, which is kept. If a folder already holds a reading that passed the gate, `run` writes no second reading (`gated_reading` in `protocol/run_scored.py`), logs which folder it found, and the first gated reading is the one reported.

The pause. The command `run_scored.py pause` writes a pause file in the run's logs folder. Each worker then finishes the phase it is flying and starts no other. The scheduler reads the pause file again at each stage boundary and before the analysis (`Runner.pause_marked`), so no later stage and no analysis starts after a pause, even one asked for while the last phase of a stage was flying. It stops with exit status 2 before the Gazebo flights and the analysis. Running `run` again removes the pause file and continues, skipping finished phases. A pause never interrupts a phase, and learning is never paused: a pause asked for during learning takes effect when the learning runs have finished, so that every learning run of the study falls in one window of model use. The pause exists so the Mac can sleep during a run longer than a night. A phase found half-done on a restart is held under the faults rule above, and is not rerun automatically.
